# 04 · 验证：怎么算通

上架最容易犯的错不是装错，是**以为通了**。这一章给一套判通顺序和反例清单，照顺序走完才能说「节点可用」。

## 会骗人的指标

| 看起来像通了 | 为什么不算 |
|---|---|
| `ping` 通 | ICMP 与 TCP/UDP 是独立的路由与策略；ICMP 通而端口全封很常见 |
| 本机 `nc -z <IP> <PORT>` OPEN | 工作机挂透明代理时，代理先握手，**任意**境外 IP:端口都显示 OPEN |
| 服务端 `ss` 显示在听 | 只证明进程起了，不证明外面能进来 |
| 面板显示「已放行」 | 只证明平台配置写了，不证明链路放行 |
| 客户端显示「已连接」 | 只证明内核吃了配置，不证明能出网 |
| 延迟数字很小 | url-test 的延迟是内核探活，可能走了本地直连 |

## 判通顺序（四步，逐步收紧）

### 第 1 步 · 服务端在听

```bash
ssh -p <SSH_PORT> root@<IP> 'ss -lntup | grep -E "<TCP_PORT>|<UDP_PORT>"; tail -n 20 /var/log/sing-box.log'
```

要求：端口在听 + 日志无 `panic` / `permission denied` / `address already in use`。

### 第 2 步 · 本机回环（绕过网络）

服务端自己开一个 socks 入站（`127.0.0.1:10888`），从机器内部验证协议栈与凭据都对：

```bash
ssh -p <SSH_PORT> root@<IP> 'curl -s --socks5-hostname 127.0.0.1:10888 https://icanhazip.com'
```

回显**本机公网 IP** = 协议、凭据、路由都对。这一步不通就是配置问题，别往网络上找。

### 第 3 步 · 外部 vantage（真正的外部视角）

从工作机用 `client-test.json` 起一个临时客户端，走真实端口：

```bash
# 工作机，绕开本地代理与规则
sing-box run -c client-test.json &
curl -s --socks5-hostname 127.0.0.1:20888 https://icanhazip.com    # 期望 = 目标机 IP
curl -s --socks5-hostname 127.0.0.1:20888 https://www.gstatic.com/generate_204 -o /dev/null -w '%{http_code}\n'   # 期望 204
kill %1
```

**这一步是分水岭**：它同时验证了「端口从外网可达」+「凭据可用」+「出口是这台机器」。

### 第 4 步 · 客户端真流量

手机 / 路由器上：

```bash
curl -s https://icanhazip.com                                   # 普通境外 → 目标机 IP
curl -s https://chatgpt.com/cdn-cgi/trace | grep -E '^ip=|^loc='  # AI 类 → 该出口
curl -s -o /dev/null -w '%{http_code}\n' https://www.youtube.com  # 200
```

再看规则真的生效：

```bash
# 路由器上
S=$(sed -n 's/^secret: *//p' /etc/openclash/zijian.yaml | head -1 | tr -d '"')
curl -s -H "Authorization: Bearer $S" http://127.0.0.1:9090/rules | jq -r '.rules[]|select(.payload|contains("<关键字>"))|"\(.payload) -> \(.proxy)"'
```

四步全过才算「通」。只有第 1、2 步过 = 服务端没问题，链路有问题——回 [01 步骤 3](01-开工前：先测什么.md) 重测端口。

## 速度与线路质量

同一台机器、同一时段，两种协议经常差一个数量级。别只测一种就下结论：

```bash
# 目标机上用 curl 拉一个大文件，分别经 socks5 的 TCP 与 hy2 端口
time curl -s -o /dev/null --socks5-hostname 127.0.0.1:10888 https://speed.cloudflare.com/__down?bytes=50000000
```

实测过的典型值（大陆 → 低价 NAT 机，**晚高峰**）：

| 协议 | 吞吐 |
|---|---|
| Reality / TCP | 0.2 – 1.3 MB/s |
| Hysteria2 / UDP | 2.7 – 4.4 MB/s |
| Hysteria2（快的机器） | 6.7 – 7.9 MB/s |

差距的来源不是加密开销，是**拥塞控制对丢包的反应**：TCP 一丢包就减窗，hy2 的 Brutal 按固定速率发、不因丢包降速。所以丢包线路优先 hy2。

⚠️ Brutal 会**无视实际带宽持续灌包**。共享母鸡必须 `ignore_client_bandwidth: true`，否则你的节点会把整台母鸡的出口打满、被平台清退。

## IP 质量体检

不是必需，但决定能不能用来登录账号、看流媒体：

```bash
# 目标机上（依赖 bash jq bc netcat-openbsd bind-tools iproute2）
bash <(curl -fsSL https://IP.Check.Place)
```

关注三件事：**IP 类型**（住宅/机房）、**风险评分**、**流媒体解锁**。机房 IP 被 Netflix 判 proxy 很正常，别指望低价机解锁流媒体；AI 服务对机房 IP 更宽容，但对**频繁换 IP** 敏感（这就是 `AI` 组要钉死的原因）。

输出存 `ip-quality.txt`，作为「这台机器适合干什么」的依据。

## CF 隧道（可选，用于 TCP 被封时的救援通道）

原理：目标机出站连 Cloudflare，外部走 CF 的 443。**不需要平台放行任何入站端口**，也不需要公网 IP。

```bash
# 配置里加一个只监听回环的 WS 入站
#   "listen": "127.0.0.1", "listen_port": 18080, transport: ws, path: <WS_PATH>

# 目标机装 cloudflared 并用命名隧道（token 方式，写 600 文件）
cloudflared tunnel --no-autoupdate run --token "$(cat /etc/cloudflared/token)"
```

验收：客户端连 `<域名>:443` + `ws` + `path`，`curl --socks5-hostname` 回显目标机 IP。
注意：**CF 免费版会限速**，它是保底通道不是主力；`-cf` 形态在订阅里默认被摘出 `YouTube` 组就是这个原因。
